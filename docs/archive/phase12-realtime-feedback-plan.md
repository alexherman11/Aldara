# Phase 12 — Near-Real-Time Pronunciation Feedback

## Goal

Annotations land on the learner's transcript bubble within ~500ms of speech ending. Sofía sees those annotations when generating her reply — so her response is informed by what the pronunciation engine actually heard, not just by Deepgram's auto-corrected transcript. The whole thing should feel like Sofía *understood* what was hard, not like a separate scoring system bolted on.

Out of scope: drill mode (Sofía-pinned reference text), post-session pronunciation reports, mobile/iOS WebRTC quirks. Those are Phase 13.

---

## A reality check before designing

Your mental model is: "Azure scores words mid-paragraph and Sofía sees them as they arrive." Worth being precise about what Azure actually does, because it shapes the design.

Azure Speech SDK has two events:

- **`recognizing`** — fires every ~100ms with a partial transcript. **No pronunciation scores.** This is a draft text result, nothing more.
- **`recognized`** — fires once per *utterance* boundary (silence-delimited segment), with full pronunciation scores for that segment.

So genuine per-word streaming feedback while the learner is mid-sentence isn't possible — pronunciation arrives at sentence boundaries, not word boundaries. But two things make the experience feel almost the same:

1. In push-to-talk, the typical learner turn is one utterance, so we get one PA result. If we feed audio to Azure *concurrent with capture* (instead of buffering and sending the whole WAV at end-of-turn), Azure has been processing the entire time and the result lands ~200–500ms after PTT release instead of ~1200ms.

2. For longer multi-sentence turns, Azure's internal VAD splits the audio and fires `recognized` for each sentence. So a paragraph-long turn yields per-sentence PA scores as it's spoken. From the UI, this looks like words lighting up sentence-by-sentence — much closer to "live."

The trade-off worth taking: gate Sofía's LLM call by up to 500ms to give Azure time to finish. Adds half a second of perceived latency to every turn, in exchange for Sofía actually responding to pronunciation rather than ignoring it. Most users won't notice 500ms; everyone will notice "Sofía gets it."

## UX design — what the learner sees

### Transcript bubble (web UI)

Two visual states for problem words, both subtle:

| State | Color | Trigger |
|---|---|---|
| Low confidence / STT-Azure mismatch | yellow tint | Deepgram word confidence < 0.85 OR Azure's recognized text disagrees on this word |
| Mispronunciation | orange tint | Azure accuracy_score < 70 OR `error_type` is anything other than `None` |

Both states: faint background tint on the word itself (no border, no shadow — meant to be peripheral), with a small annotation row below the bubble showing details in dimmer text. On hover or click of the annotated word, expand the full breakdown (phoneme arrows, alternate words, full score).

### Inline bracket annotation format

After each transcript line, on its own dimmer line:

```
me encanta el perro grande
  [.62 perro, .38 pero]                       ← Deepgram alternates with confidence
  [pron 62 — perro, /r/→/ɾ/, /e/→/ɛ/]        ← Azure score + phoneme substitutions
```

When both apply to the same word, both lines appear stacked. The brackets are visible in the UI and *also* fed verbatim to Sofía's prompt, so what she "sees" and what the user sees are aligned. (Important: if the learner glances at the debug panel and Sofía's reply, they shouldn't see different stories.)

### Format rules

- `[.62 perro, .38 pero]` — alternates ranked by Deepgram confidence. Only shown when top alternate ≥ 0.30 and primary < 0.85 (otherwise there's no real ambiguity).
- `[pron 62 — perro, /r/→/ɾ/]` — Azure pronunciation hint. Up to 3 phoneme substitutions, single word per annotation. (Already implemented in `formatAnnotation`.)
- One line per type. Don't merge — they're different kinds of signal and Sofía needs to read them differently.

### Streaming behavior

During the turn:
- Learner presses PTT, speaks.
- Transcript bubble appears with raw Deepgram partial text as it streams in (already works today via Deepgram's `interim` events).
- No annotations yet.

After PTT release:
- Deepgram finalizes (~100ms).
- Bubble updates to final transcript text.
- Azure finalizes (~200-500ms with streaming pipeline).
- Annotations appear: word backgrounds tint, bracket lines fade in below the bubble.
- Up to 500ms after PTT release, Sofía's LLM call kicks off with the annotated prompt.

If Azure is slow (≥500ms):
- Sofía's call proceeds without annotations to avoid stalling the conversation.
- When Azure does land, the annotation lines fade in (transcript bubble retroactively updates) but Sofía's reply text — already generated by then — is not modified.

This is the "preserve Sofía's generated words" piece. The learner sees the bubble gain feedback while Sofía starts speaking; nothing is jarring.

## Architecture changes

### 1. Pronunciation pipeline → streaming push mode

**Current:** `recognizeOnceAsync` with a closed push stream containing the full WAV.

**New:** start `startContinuousRecognitionAsync` when PTT_start fires, push frames into the stream as they arrive from the `sttNode` tee branch, close stream and collect final `recognized` event on PTT_end.

Concrete changes to [src/agent.ts](src/agent.ts):

- Replace `currentTurnFrames` batching with direct push to an `AzureStreamingSession` object.
- Open a session in the `ptt_start` RPC handler.
- Close + collect result in the `ptt_end` RPC handler.
- The agent now has a *pending pronunciation promise* per turn — `onUserTurnCompleted` awaits it (with a 500ms cap) before kicking off the LLM call.

Concrete changes to [src/pronunciation/azure-assessor.ts](src/pronunciation/azure-assessor.ts):
- Add `startStreamingSession(referenceText): AzureStreamingSession` method alongside the existing `assess()`.
- `AzureStreamingSession` exposes `pushFrame(pcm)`, `finalize(): Promise<PronunciationAssessment>`.
- Assessment lifetime is now bound to PTT-start/PTT-end, not to end-of-turn.

Important caveat: Azure's `recognized` event fires per *utterance*. For a multi-sentence learner turn, multiple events fire. `finalize()` should collect *all* segments and merge them into a single `PronunciationAssessment` for the whole turn (concatenate word arrays, average overall scores weighted by word count).

### 2. Surface Deepgram confidence + alternates to Sofía

Today [src/agent.ts:128-145](src/agent.ts:128) reads only `newMessage.content` from the LLM-style chat context. Deepgram's raw response has more: per-word confidence, n-best alternative transcripts. Need to grab these from the upstream STT event.

Specifically:
- LiveKit Deepgram plugin exposes `STTEventTypes.RecognitionResults` with `alternatives` and per-word `confidence` on each alternative.
- Hook this in `agent.ts` near where we already listen for `UserInputTranscribed`.
- Stash low-confidence words (per-word confidence < 0.85) and top alternates on the session context, keyed by turn number.
- The prompt-builder picks these up at next prompt rebuild.

New format in the prompt:

```
[learner] me encanta el perro grande
  [stt 0.62: perro / 0.38: pero]
  [pronunciation] perro: 62 (Mispronunciation, /r/ → /ɾ/)
```

Tested format suggestion (matching your example): `[.62 perro, .38 pero]`. Lowercase, no leading dot space, comma-separated. Easy to grep, easy for the LLM to parse.

### 3. LLM-gating logic

In `onUserTurnCompleted`:

```ts
async onUserTurnCompleted(chatCtx, newMessage) {
  // existing transcript append + difficulty kickoff

  const annotationPromise = this.streamingAssessor.finalize();
  // Race: either annotation arrives in 500ms or we proceed without it
  await Promise.race([
    annotationPromise,
    new Promise((r) => setTimeout(r, 500)),
  ]);
  // If finalize resolved already, the prompt is rebuilt with annotations
  // before LLM kicks off. If timeout won, LLM uses the plain transcript;
  // annotation lands ~later and updates UI only.
}
```

The 500ms is a hyperparameter. We can lower it (faster but less coverage) or raise it (slower but Sofía always sees). I'd start at 500ms, watch how often Azure beats it in real sessions, and tune.

### 4. UI annotation rendering

[web/app.js](web/app.js) needs a richer transcript renderer:

- Replace plain `textContent = msg.text` with a token-by-token DOM build.
- Each token is a `<span class="word">` with `data-confidence` and `data-pron-score` attributes.
- Below each transcript bubble, an `.annotations` block with bracket lines.
- New RPC `pronunciation_update` from the agent → browser, fired when streaming assessment finalizes, carrying the per-word + alternates payload. UI updates the matching bubble in-place.

[web/style.css](web/style.css):

```css
.word[data-pron-score="low"]      { background: color-mix(in srgb, #ff8800 18%, transparent); }
.word[data-confidence="low"]      { background: color-mix(in srgb, #ffcc00 18%, transparent); }
.word:hover                       { background: rgba(255,255,255,0.05); }
.annotations                      { font-size: 0.82em; opacity: 0.65; margin-top: 2px; }
.annotation--pron::before         { content: '⌗ '; opacity: 0.5; }
.annotation--stt::before          { content: '⌖ '; opacity: 0.5; }
```

(Keeping it subtle — peripheral, never gets in the way of reading the conversation.)

## Testing plan additions

Three things the previous stress harness didn't cover:

1. **Multi-voice synthesis.** Cartesia has many Spanish voices. Synthesize the same phrase across 5-6 of them to verify Azure isn't fragile to voice character. Also try OpenAI TTS with English voices ("alloy", "echo") reading Spanish — those genuinely produce L1-influenced audio because the models aren't trained on Spanish.

2. **Aggressive garbling.** Beyond input-text mutation: speed-perturbation, additive white noise at 10–20 dB SNR, mid-word clipping, sample-rate downsampling (8kHz simulating phone audio). Verifies Azure degrades gracefully across acoustic conditions a real microphone will introduce.

3. **Real L2 audio (aspirational).** I'll investigate accessible corpora — Mozilla Common Voice Spanish (native but high voice variance), VoxForge Spanish, OpenSLR — and document what's openly downloadable. If nothing pans out automatically, the honest fallback is: **the only true test is Layer 5 with a real learner.**

A new script `scripts/test-pronunciation-stress-v2.ts` will cover items 1-2. Item 3 gets a separate investigation note.

## Risks and what could go wrong

1. **500ms gate adds perceived latency to every turn.** If Azure typically takes 200ms with streaming, fine. If 400+ms is common, conversation feels sluggish. Mitigation: instrument and lower the gate adaptively.

2. **Streaming Azure has different failure modes.** Push stream may stall, recognizer may emit no `recognized` event, network blips during long utterances. Need a watchdog that abandons the streaming session and falls back to today's batch path.

3. **Annotation arrives AFTER Sofía replies sometimes.** UI retroactively updates the bubble. Some users may find this disorienting ("the system rewrote my message"). If so, gate the UI update behind a small "just finished scoring" badge that fades in rather than a hard text replacement.

4. **Multi-utterance turns may yield contradictory PA scores.** A single turn could contain "Hola" (clean) and "perrrro" (mispronounced) and Azure returns two `recognized` events. Merge logic needs to handle this — weight by word count, not by event order.

5. **STT alternates are not always informative.** When Deepgram is highly confident, the n-best is just the same phrase reshuffled. Filter out alternates that differ from the primary by <2 words OR by trivial punctuation.

6. **The "el mio vs el mar" case still won't be caught by pronunciation.** That's a lexical/semantic error, not acoustic. The LLM has to catch it. We help by surfacing Deepgram's per-word confidence — if the learner pronounced "mar" but Deepgram heard "mio" at 0.65 confidence, the LLM sees `[.65 mio, .30 mar]` and can probe. But if Deepgram heard "mio" at 0.95 confidence and the learner really did say "mio," Azure will score it cleanly and there's nothing more to do — that's a vocabulary lesson, not a pronunciation one.

## Order of work

I'd ship these in this order, each independently useful:

| Phase | Scope | Reason this order |
|---|---|---|
| 12.1 | Visible UI feedback for existing (batch) pipeline | Highest value-per-effort. The signal already exists. Users see something working today. |
| 12.2 | Deepgram confidence + alternates → LLM prompt | Cheap. Catches the lexical-error class the pronunciation engine can't catch. |
| 12.3 | Streaming Azure + 500ms LLM gate | Bigger refactor. Should follow once 12.1 lands and we know the UI surface works. |
| 12.4 | Post-LLM bubble update (when Azure misses gate) | Polish. Only needed if step 12.3 hits the timeout often in practice. |

Each phase has a clear "definition of done" test:
- 12.1: a real session in the browser shows yellow/orange word tints + bracket lines within 2s of every turn.
- 12.2: the agent log includes `[.62 perro, .38 pero]` lines in the system prompt for at least one turn with ambiguous audio.
- 12.3: end-to-end turn latency (PTT release → Sofía first audio out) increases by ≤500ms, and ≥70% of turns have annotations available when Sofía generates.
- 12.4: when annotation lands after Sofía starts, the transcript bubble visibly updates without disrupting Sofía's audio.

## Open questions for you to decide

1. **Color choice.** Yellow/orange are easy to confuse with each other under colorblindness. Acceptable, or do you want a different palette? (Suggestion: yellow for low-confidence is fine, but consider a desaturated red for mispronunciation since "orange near yellow" can look like one continuous gradient.)

2. **Where do brackets appear?** Two options:
   - **Below the bubble** (current proposal): clean reading, brackets are dimmer companion text.
   - **Inline** (`me encanta el [.62 perro, .38 pero] grande`): denser, more disruptive when reading, but no extra vertical space.

3. **Should pronunciation feedback ever interrupt Sofía?** Right now the model is "annotation influences her next reply." Should there be a "drill" mode where a really bad score triggers Sofía to *stop and probe* the same word? I think no — too disruptive — but worth confirming.

4. **Latency budget.** 500ms gate is my starting point. Anything you'd like that to be capped at differently?

## Empirical findings (test v2 run after writing this plan)

`scripts/test-pronunciation-stress-v2.ts` ran 19 cases across 5 groups against the live Azure endpoint. Full data in [phase12-stress-v2-results.json](phase12-stress-v2-results.json). Headline numbers:

| Group | n | Avg accuracy | Range | Avg latency |
|---|---|---|---|---|
| A. Cross-voice clean (Cartesia, 5 voices) | 5 | 85.4 | [83, 88] | 1141ms |
| B. English-trained voices reading Spanish (OpenAI alloy/echo/nova) | 3 | 46.3 | [10, 88] | 1003ms |
| C. Aggressive garbling (mutated input text) | 5 | 76.8 | [65, 88] | 1306ms |
| D. White noise (SNR 30, 20, 10, 5, 0 dB) | 5 | 90.4 | [89, 91] | 1173ms |
| E. 8 kHz phone-quality downsample | 1 | 88.0 | — | 942ms |

**Cross-engine sensitivity (clean Cartesia − L1-influenced OpenAI): 39.1 points.** That's the headline. The pipeline differentiates between near-native and L1-influenced Spanish by a wide margin — wider than the v1 test's 20.8 points because the OpenAI voices produce genuinely English-flavored Spanish rather than synthetic mutations.

What this tells us about the plan:

- **Voice variance is not a problem.** Five different Cartesia voices all clustered within 5 points (83–88). Whatever the user's microphone or accent character is, Azure will produce a stable score floor.
- **L1 transfer is caught sharply.** OpenAI `nova` reading Spanish dropped to 10 accuracy with full STT/Azure divergence — Azure heard "Hola Madrid" instead of the full sentence. The divergence flag fires correctly for the worst cases. This is the strongest evidence yet that the new STT/assessor-mismatch annotation surface will be useful in practice.
- **Noise robustness exceeds expectations.** Even at 0 dB SNR (signal == noise) the engine returned ~91 accuracy. We do not need to worry about a busy cafe or a humming AC degrading scores below threshold. If anything, this is suspiciously good — the engine may be smoothing noise out of its analysis. Worth verifying with truly garbled mic audio at user-test time.
- **8 kHz works fine.** Phone-quality audio (downsampled) scored 88 — identical to the 16 kHz clean baseline. The pipeline is tolerant to bandwidth-limited inputs.

What this surfaces that's worth handling:

- **Proper nouns persistently score low across all voices.** "Carlos" and "Madrid" flagged in all 5 cross-voice tests (32–69 score range), even on native Spanish synthesis. Azure's phoneme model probably doesn't have strong templates for capital-letter proper nouns. We should either filter proper nouns from `formatAnnotation` flagging (detect via case or NER) or surface the limitation in the persona ("don't react to flags on Carlos / Madrid / etc."). Either way, this is something Sofía will see and shouldn't react to as a real pronunciation issue.
- **`openai-echo` voice scored a surprising 88** while alloy got 41 and nova got 10. Voice-character variance matters; we can't assume any English TTS voice produces L1-influenced audio uniformly.
- **Latency is consistent ~1.0–1.3s** across conditions. With streaming push (Phase 12.3), this drops to roughly the duration of the *last utterance segment after PTT release* — likely 200–500ms.

### L2 audio corpus investigation

Searched openly-downloadable L2 Spanish corpora. **There aren't any in a script-friendly form.**

- **L2-ARCTIC** ([Hugging Face](https://huggingface.co/datasets/KoelLabs/L2Arctic)) is L2 **English** from L1-Spanish speakers — the inverse of what we'd want.
- Common Voice Spanish is large and openly licensed but native-speaker only.
- UDC's research on L2 Spanish ASR ([paper](https://portalinvestigacion.udc.gal/documentos/688bae90443ab7739464f1ea?lang=en)) uses an internal corpus.
- CLARIN's L2 corpora directory lists academic L2 Spanish sets but they require institutional access.

The honest fallback: **OpenAI English-trained TTS reading Spanish is the closest reproducible proxy for L2 audio we can use in CI**. We've now validated it produces realistic L1-transfer characteristics (acc range 10–88). The true sensitivity test still requires a real A1–A2 learner — that lands in Layer 5 of [phase11-test-plan.md](phase11-test-plan.md).

### Implications for the plan

Plan stands. The streaming + 500ms gate design is justified by the data:
- Azure latency is ~1s consistently. Streaming should pull this to ~300ms post-PTT.
- The 39-point sensitivity gap means there's real signal worth waiting for — gating Sofía's LLM call is not a tax on noise.
- The divergence flag fires hardest exactly when we need it most (Group B alloy/nova). The STT/assessor-mismatch UI surface is high-value.

Minor adjustments worth folding into the implementation:
1. **Proper-noun filter** in `formatAnnotation`. Either case-based (`/^[A-Z]/`) or list-based for the most common offenders. Add as a small follow-up before shipping 12.1.
2. **Watch the noise robustness claim under real conditions.** If real user audio under noise produces dramatically different scores than the synthetic-noise test (it might — real mic noise has structure), revisit.

## Design decisions (locked in)

- **Inline annotations** in the transcript bubble itself, not on a separate line. Denser but every annotation is immediately tied to the word it describes.
- **Gradient palette** instead of binary tinting:
  - Score ≥85: no tint (clean)
  - 70–84: pale yellow (`#fff3a3` at low opacity)
  - 55–69: yellow-orange (`#f5a623`)
  - 40–54: orange (`#e8741a`)
  - <40: red (`#d44a3a`)
  - STT divergence (any score): dashed yellow underline overlay
  - **Above-level vocabulary the learner stretched into**: green tint (`#5ec76e`)
- **No latency gate.** LLM call fires ASAP once Deepgram finalizes. Pronunciation data flows in concurrently and:
  - If it lands before LLM starts → goes into the prompt
  - If it lands during LLM generation → goes into the next turn's prompt + UI bubble updates retroactively
  - If it lands during Sofía's TTS → bubble updates, next turn's prompt has it
  - **In-flight LLM generations cannot see data that lands after they started.** OpenAI's streaming API doesn't support mid-stream context injection. So "always has the most up-to-date info" is true for future generations and the UI; current generation gets a best-effort snapshot.
- **Drill mode**: deferred to Phase 13.

## Green for above-level words — design

Tags vocabulary the learner *stretched into* (used a word they didn't have comfortably). Encouragement signal in the same UI dimension as pronunciation warnings.

Heuristic for v1 (cheap, no extra calls):
- A word is "above-level" if it matches an FSRS card that is **due, but in `state >= 1`** (learning/review state). These are the words Sofía has been scaffolding — the learner producing them unprompted is exactly what we want to celebrate.
- Also flag any word in `tutor_core.fsrs_integration` description that's not in the learner's `comfort_zones`.

Later: pair with a Spanish CEFR frequency list (Subtlex or CORPES XXI) so we can highlight novel low-frequency words even without an FSRS match.

Display: same word-span styling, just green instead of yellow/red. Tooltip on hover says "above your usual level — nice." Sofía's prompt gets a `[stretch]` marker on those words so she can naturally affirm them.

## Inline annotation format

Renders the same in UI and prompt — single canonical format. The brackets contain everything tied to that word; click/hover for full breakdown.

```
[learner] me encanta el perro[62 /r/→/ɾ/] grande
[learner] me encanta el [.62 perro, .38 pero] grande
[learner] ayer fui al mercado[stretch] con mi familia
```

Format rules:
- `word[score phoneme→sub]` — pronunciation flag. Score in plain integer, phoneme arrow only when present.
- `[.62 word, .38 alt]` — STT alternates, ranked. Replaces the word entirely in the rendered text since they're competing hypotheses.
- `word[stretch]` — above-level word.
- Multiple flags on same word: combine inside one bracket: `perro[62 /r/→/ɾ/ stretch]`.

The UI renders each `[...]` token with a smaller font and dimmer color so it doesn't disrupt reading; the word itself carries the color tint per the gradient.

## Implementation order (revised)

1. **Phase 12.1 — UI inline annotations + green stretch tagging** — visible win first. Uses existing batch (non-streaming) pronunciation. Reuses `formatAnnotation` rewritten to inline.
2. **Phase 12.2 — Deepgram confidence + alternates → prompt** — surfaces the lexical-error dimension. Small refactor in agent.ts to grab STT n-best from LiveKit events.
3. **Phase 12.3 — Azure push-stream during the turn** — drops post-PTT latency from ~1.2s to ~300ms. No gate; UI updates on arrival.
4. **Phase 12.4 — `pronunciation_update` RPC** — agent → browser push when assessment lands post-LLM-start, so the bubble retroactively annotates.

Each step is verifiable in browser end-to-end before the next.
